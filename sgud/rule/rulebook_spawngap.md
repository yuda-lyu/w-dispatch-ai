## R-SPAWNGATE-4 放行最小間隔 `minGapMs`(Gitea #85)

- 規則:①守門物件增 `minGapMs`:距「上一次放行」不足即補足剩餘時距再放行(`need = minGapMs − 已過時距`,只補不足的);②預設:**`opencode` 為 1500 ms,`claude`／`codex`／`antigravity` 預設 `null`(不錯開,行為不變)**;`false` 關閉;`spawnGate: false` 整個守門不運作故不受影響;假 CLI／包裝腳本未明給 `spawnGate` 者仍不守門;③輸入檢測依 `cliSpawnGate.mjs` 檔頭〈輸入檢測〉:正數毫秒(`isenum timer`,上限 2147483647,數字字串收下並轉換,K4),`false` 關閉,`undefined`／`null` 取預設,其餘(0、負數、`NaN`、`Infinity`、超上限、物件、陣列、`true`、函數)視為未給改用預設而不報錯(K3),`debug: true` 時 `warn` 一行指出鍵名與預設、不含傳入之值(K9);④**等待在互斥臨界區內、檢查之前**(`lock` → 補足間隔 → `evaluate` → `reserve`):同行程併發呼叫 FIFO 依序錯開,且「最後一次讀取」仍緊接登記預約;與被擋後輪詢之 `sleep(pollMs)` 無關;⑤歸屬同既有守門等待:**不計入 `timeoutMs`**(守門在 spawn 之前);**計入 `deadlineAt`(`budgetMs`)**:單次等待 `ms = min(需補, max(0, 截止 − 現在))`,截止＝`min(t0＋gateWaitMaxMs, deadlineAt − minAttemptMs)`(`deadlineAt` 為使用端自給者與遞補層期限之較早者,R-COOL-5),到點不再等而放行(事件 `capped: true`),**不標 `failOpen`**(間隔只降低競爭機率,不是放行條件);等待後 `shouldStop` 為真則中止(outcome `aborted`),臨界區必釋放;`sleep` 拋錯 → 守門 fail-open 且臨界區釋放;⑥「上一次放行」＝max(本行程記憶體〔狀態物件之 `lastRelease`,不隨 `settleMs` 剔除〕, 他行程預約票〔窗口取 `max(settleMs, minGapMs)`,不含本行程之票;不晚於現在〕);**票之寫入條件由「限行程數」擴為「限行程數或錯開間隔」**;票仍是提示非鎖(已知限制②不變);⑦**間隔不單獨啟動守門**:行程數／RAM／CPU 皆 `false` 且**未明給** `minGapMs` 時仍 `resolveSpawnGate` 回 `null`(`outcome: 'off'`,與修前相同);**明給** `minGapMs` 才成為只錯開、不查任何探針之守門;⑧觀察回調新增 `gap-wait { ms, minGapMs, sinceLastMs, capped }`(臨界區內、距上次放行不足時才發;`ms` 為實際等待〔受截止截斷後可為 0〕),凍結、同步、拋錯忽略,不另記 log;⑨預設值 1500 之依據見上表(啟動窗口約 1 秒、冷資料庫相隔 1500 ms 者 3／3 成功),**為推論值**。
- 已知限制:①預設值未經「近同時啟動、已就緒資料庫、真模型」之直接驗證(回報字樣未重現,見上);②N 個併發之最後一個多等約 (N−1)×1.5 秒(opencode 單次呼叫秒級～數百秒,影響次要;不要者 `minGapMs: false`);③跨行程以票為準,兩行程於同一毫秒內讀寫仍可能各放行(同 R-SPAWNGATE-1 已知限制②),殘餘風險靠 R-SPAWNGATE-5 兜底;④被行程數／CPU 擋住而輪詢者,每次進臨界區時也會補足剩餘時距(無害:其時距通常早已足夠);⑤放行時刻以「通過檢查並登記預約」為準,不含其後 spawn 之數十毫秒(execCli 逐一 spawn);⑥預算耗盡時間隔被截斷,仍可能與前一個同刻放行(預算優先);⑦互斥鎖為狀態物件層級(不分 images key),且間隔等待在鎖內:同行程中另有「明給守門」之其他 CLI(預設 claude／codex／antigravity 無守門,不受影響)其檢查會排在 opencode 之間隔等待之後(外審指出;修前臨界區只含檢查,約 0.07～1.1 秒);⑧排隊等鎖之時間不受截止約束:N 個併發且有 `budgetMs` 時,排在後面而取得鎖時已逾「期限 − `minAttemptMs`」者不再等待、放行,其 `timeoutMs` 以剩餘預算封頂(可能小於 `minAttemptMs`,易逾時),`shouldStop` 僅在實際等待(ms>0)之後才檢查——與既有「被擋後 fail-open」同一取捨,吞吐上限約每 1.5 秒放行一個;⑨被行程數／RAM／CPU 擋住後之 fail-open 放行(`reserve` 在鎖外)與截斷後之放行都不保證相鄰 ≥ `minGapMs`(間隔是降低競爭機率而非放行條件)。

## R-SPAWNGATE-5 opencode 暫時性錯誤(`database is locked`)重試一次(Gitea #85)

- 規則:①實作於 `runExecCli`(單一入口),**只在 `spawnGateKind === 'opencode'`**(claude／codex／antigravity 與未給 kind 者行為不變);②辨識 `isTransientFailure(r, fastMs)`:`ok` 非真、`error` 不以 `TIMEOUT` 開頭、`durationMs`(單次嘗試耗時)為數字且 `< fastMs`(預設 15000)、且 `stderr` 含 `/database is locked/i`——或 `stdout` 有 `type` 為 `error` 且該行含此字樣之事件行(`--format json` 未經還原者;`detectTruncation` 還原後之錯誤已併入 `stderr`);**stdout 純文字不算**(模型輸出可能談到資料庫);正規式為**內部常數、不開放配置**(日後真有第二個已知字樣再開);③流程:辨識成立 → `shouldStop` 未成立 → 預算夠(有 `deadlineAt` 時:`deadlineAt − 現在 − 延遲 ≥ minAttemptMs`,`deadlineAt` 取 spawnGate 物件與遞補層提示之較早者〔排程第 417 項,R-COOL-5〕,`minAttemptMs` 取 spawnGate 物件、遞補層提示、預設 20000) → 等延遲(預設 2000 ms) → 再判 `shouldStop` → **再過守門**(含 R-SPAWNGATE-4 之間隔) → **單獨再跑一次**(`execCli` 之 `maxRetries` 0;**該輪 `timeoutMs` 另以期限封頂 `min(守門後之 timeoutMs, deadlineAt − 現在)`,守門未運作〔`spawnGate:false`、假 exe 預設情形〕時亦然**——外審指出:首次耗時與延遲已用掉預算,沿用原值會超出期限);④**獨立於 `maxRetries`、不佔其次數**,每次呼叫(含有 `validate` 時之各輪)**至多一次**;`attempts` 照實累計(兩段之和;有 `validate` 時 `used + trAtt`,`used` 仍只含計入預算者);⑤仍失敗則原樣交遞補層:`errorType` 仍為 `exec`(`getErrorType` 不變:離開碼 1 一律 `exec`)、結果形狀不變(只 `attempts` 多計);成功結果形狀與一般成功相同;⑥不重試:非 opencode、逾時、失敗很慢(≥15 秒)、其他錯誤字樣、截斷(`incomplete`)、驗證失敗、`shouldStop` 成立(回**原失敗**而非 `ABORTED`;重試前之守門才被中止時回 `ABORTED`,`attempts` 為已嘗試次數)、遞補層預算不足;⑦`opt.transientRetry = { delayMs, fastMs }` 為**測試用注入**(逐鍵檢測,非預期之值改用預設),不轉傳 `execCli`;不在 README 選項表列出;⑧**觀察回調**(dspec〈計時器相關函數之觀察回調與測試〉):決定重試時(等延遲之前)經 `opt.onTrace`(與 `execCli` 同一回調,以 wsemi `getTrace` 取得:凍結事件、同步、拋錯與 rejection 忽略、未給時不組事件)發出 `transient-retry { n(已嘗試次數), ms(重試延遲), durationMs(該次失敗耗時) }`,不含輸出內文;事件表示「已決定重試」,延遲中 `shouldStop` 轉真則其後不再重試。
- 已知限制:①辨識只認 `database is locked`;本機**未能重現該字樣**,重現到的冷資料庫建表競爭(訊息為 `Failed query: CREATE TABLE …`,不含該字樣)**不被辨識**,故不重試(該情境只在新資料夾首次啟動;是否納入為第二字樣待裁示);②每次辨識成立至少多 2 秒＋守門時距;③`attempts` 由 1 變 2 對「假設 `attempts ≤ maxRetries＋1`」之呼叫端有感(屬提案之要求);④「不佔其次數」在觀察上與「佔」等價(execCli 回失敗時預算必已用盡,見變異 E01／E02),保留為記帳語意;⑤`durationMs` 為最後一次嘗試之耗時(execCli 語意);⑥stderr 被裁(失敗 1000 字元)、自給 `--format json` 時 stdout 被裁(500 字元)而字樣在其後則辨識不到(啟動期失敗之輸出很短,影響次要);⑦**重試會重跑整個提示詞**:故 stdout 已有 `tool_use` 事件者不重試,交遞補層或呼叫端判斷(主控 2026-11-05 定;啟動期失敗之 stdout 為空,不受影響;遞補層換家同樣會重跑提示詞,此處只擋「同家多跑一次」);自給 `--format json` 時 stdout 被裁 500 字元,事件在其後則辨識不到;未輸出 JSON 事件之格式無從判斷;⑧重試沒有關閉開關,判準是 `spawnGateKind` 而非 exe(`spawnGate:false` 關不掉,假 CLI 在 kind 為 opencode 時同樣重試;測試即利用此點);⑨第一次失敗之 `stderr` 不留痕(結果只含最後一次;無 trace/log 接點),只能由 `attempts` 推知。
